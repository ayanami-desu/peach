# 目录浏览

目录浏览按账本里的虚拟路径拼目录树：路径形如 `gdrive:/Movies/2024/a.mp4`，第一段是网盘来源，后面每一段是远端目录名。拼树只读账本，不访问网盘，也不需要在服务器上放一份对等的目录结构——树里有什么完全取决于扫描登记了什么。

## 虚拟路径

- 第一段写作 `<location>:`，界面上显示来源名字（Google Drive、OneDrive），不显示 id。
- 同名目录按来源分开：`gdrive:/Movies` 与 `onedrive:/Movies` 是两个节点。
- 路径比较不分大小写，目录名里的 SQL 通配符（`%`、`_`）按字面匹配。
- 节点 id 是 `sha256(location + '\0' + path.casefold())` 的前 24 位十六进制，同一条路径永远同一个 id。
- 已进回收站或已从远端消失的资产（`disposal` 为 `trash`、`vanished`）不参与拼树；因此空目录不出现，只有登记过文件的那几层才会成为节点。
- 每个节点带 `files` 与 `videos` 两个计数，`has_children` 说明往下还有没有登记过的目录。计数是子树累计值。

扫描是目录树的唯一来源。增量同步每 15 分钟向网盘要一次变更，每 24 小时做一次全量比对；某趟有列不动的目录时这一趟不判定「已消失」，树里也就不会凭空少一层。

## 浏览接口

`GET /api/folders` 接受四个查询参数：`loc`（只留一个来源）、`library`（只留一个扫描根）、`folder`（选中的节点 id）、`q`（按目录名搜索）。返回：

| 字段 | 内容 |
| --- | --- |
| `roots` | 顶层节点，每个来源一条 |
| `children` | 当前节点的直接子目录 |
| `ancestors` | 从顶层到当前节点的路径，供面包屑 |
| `selected` | 选中的节点，没选为空 |
| `matches` | 名称包含 `q` 的节点，最多 100 条 |
| `rule`、`rules`、`rules_revision` | 当前节点的目录规则、全部规则与规则版本 |
| `conflicts` | 当前规则在这次范围里保留现有归属的条目与原因 |

节点字段：`id`、`name`、`path`、`location`、`parent`、`videos`、`files`、`has_children`。排序按名称，名称相同再按来源。

页面地址是馆藏的 `?browse=folders`；选中某个目录写进 `?folder=<节点 id>`，来源与媒体库用 `?loc=`、`?library=` 收窄。`?folder=` 给的 id 不在当前索引里时回 400「目录不存在或已移出媒体库」，`q` 最多取前 200 个字符参与匹配。

## 目录筛选

选中目录后，作品列表按 `?folder=<节点 id>` 过滤，`folder_recursive=0` 只看当前层，否则含全部子目录。判定按完整目录组件做前缀匹配，不是字符串前缀：`/Movies/202` 不会吃进 `/Movies/2024` 之外的东西。节点 id 不在当前索引里时结果为空集。

媒体库分组决定归属。扫描根登记为 `asset.drive_root`，`library` 参数按（来源，扫描根）这一对收窄，`asset.path` 只负责展示与筛选。

## 目录规则

目录规则把一整个目录的文件认作同一种用途，用途与关联对象由用户在设置里确认：

| 用途 | 关联 |
| --- | --- |
| 个人分类 `category` | 不关联实体，只记分类 |
| 创作者／账号 `creator` | 创作者实体 |
| 人物 `performer` | 人物实体 |
| 卖家 `seller` | 创作者实体，同时记一条卖家角色 |
| 厂牌 `studio` | 厂牌实体 |

`recursive` 决定这条规则管的是这一层还是连同子目录；`future` 打开时，扫描新登记的资产自动按最深的这条规则关联，关掉就只对当前这批生效。

除个人分类外都必须给关联名称（最多 200 个字符）；名称先规范化，存在多种身份或不同写法时拒绝保存并提示改用资料页的规范名称。正文里的 `recursive`（是否含子目录）与 `future` 两个开关必须是布尔值，缺一个或给别的类型回 400「目录范围与新文件设置须明确选择」；`purpose` 不认识时回 400「请选择目录用途」。

规则存在 profile 的 `folderRules` 里，带一个版本号。生效范围按最深的那条规则算：同一来源下，路径在当前目录之下且匹配 `recursive` 的规则里，取路径层级最多的那条；子目录规则因此盖住父目录规则，冲突条目在预览里给出的理由就是「由子目录规则管理」。

流程分两步：

1. `POST /api/folders/preview`，正文 `{folder, purpose, name, recursive, future}`，返回 `plan_version`、`total`、`applicable`、`withdrawn`、`conflicts`（每条带 `id`、`name`、`reason`）与 `sample`（前 6 条）；对话框最多列出前 30 条冲突，接口给的是全量。
2. `POST /api/folders/rule`，带 `action: "save"`、`plan_version` 与 `expected_revision`；提交时重算，版本或范围对不上回 409「目录规则已变化，请重新打开设置」。

`action: "remove"` 移除规则并撤回这条规则建立的关系，后来被其他操作接管的字段保持原值。关系的来源记作 `user:directory-<节点 id>`，因此撤回只影响本规则写下的那部分。目录已移出媒体库时两条端点都回 400「目录不存在或已移出媒体库」，`action` 不认识时回 400「不支持的目录规则操作」。

已有归属或逐件确认过的内容不覆盖。预览里的 `applicable` 是可应用数，`conflicts` 是要保留原归属的条目，保存后只对前者写入关系。
