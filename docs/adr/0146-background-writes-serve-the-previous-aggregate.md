# ADR-0146：后台任务写账本后，页面先拿上一份聚合

- 状态：已采纳
- 日期：2026-11-05
- 关系：修改 `WebContract.cached_until_changed` 带 `tables` 那一支的失效口径；结果版本见 `web_result_versions.py`

## 背景

目录分组快照、筛选项、榜单、索引、统计、形状名单都按依赖表的版本缓存（`cached_until_changed(..., tables=...)`）。版本一变，下一位读者就当场重算，算完才返回。

后台任务成批写账本时，这个口径让页面一直在等。2026-11-05 生产实测：补头像、补别名、采集这类后续任务每几秒提交一次，统计页第一次打开要等 3 秒，重启后定时任务集中补跑那几分钟，作品列表等了 13 秒。重算本身已经压过一轮（解析结果按输入记住），剩下的是 SQL 与聚合，压不到零。

这些写入不是用户刚做的操作。页面上晚几秒看到一条新补的头像或别名，用户察觉不到；但等 3 秒才看到作品列表，他会察觉。

## 决策

**一、区分前台与后台提交。** `repository.in_background` 包住的线程入口算后台写入者：后台任务（`BackgroundJob`）、后续任务调度（`FollowupRunner`）、云下载循环、推送发现。它们提交时，`cache_bust` 记下 `background_generation`；其余线程（请求处理、测试、显式 `cache_bust`）的提交记 `foreground_generation`。没包的线程一律按前台算，保持原有的当场重算。

**二、只有后台提交之后才先回旧值。** 带 `tables` 的键版本变了时，若手上那份出发之后没有前台提交，且本进程确有一次后台提交，就先回那一份，交给一条后台线程重算。同一个键在途时不重复排。前台提交之后照旧当场重算，写的人立刻看到自己写的。进程外的写（命令行、账本同步）不经提交通知，也当场重算。不带 `tables` 的键每次提交都被清掉，没有旧值可回，不在此列。

**三、重算写回后通知页面。** 重算写回时 `cache_landed` 加一，并拼进每个账本结果版本键（`catalog`、`review` 与 `artwork`）。页面的结果轮询看到版本变了，再取一次，拿到新值。没有这一步，最后一笔后台写入之后页面会停在旧值，直到下一次写入。

## 理由

- 判据落在「谁提交的」而不是「谁在读」：同一页面既要在后台任务刷账本时不等，也要在用户自己批准、改名后立刻看到结果，只有提交方知道这一笔属于哪种。
- 标记后台写入者、默认前台：漏标一个后台线程只是少一处加速，不会让用户的操作结果晚到；反过来标记前台，测试与请求内写完即读都会拿到旧值。
- 一条重算线程：重算多是几秒的 CPU，和请求抢同一个进程；排成一队比并发重算对页面更友好。

## 后果

- 后台任务刚写完的几秒内，页面先显示上一份，重算写回后自动换成新的。
- 每次写回都会让页面上各组读数各刷新一次；它们多半命中缓存，代价是几次轻量请求。
- 新的后台写入线程要用 `in_background` 包入口才享受这一口径；不包也正确，只是照旧当场重算。
